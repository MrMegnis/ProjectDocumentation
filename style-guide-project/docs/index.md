# Стайлгайд технической документации MenshikovAI

Это руководство задаёт правила оформления технической документации Telegram-бота MenshikovAI: описания проекта, установки, конфигурации, архитектуры, данных и тестирования. Разделы слева соответствуют структуре документации.

## Общие правила оформления

Помимо требований к содержанию отдельных разделов, для всей технической документации MenshikovAI устанавливаются единые правила языка и оформления.

### Заголовки

- Заголовки оформляются в стиле sentence case: с прописной буквы пишется первое слово и собственные имена.
- В конце заголовка точка не ставится.
- Не допускается пропуск уровней заголовков. После заголовка первого уровня используется второй уровень, после второго – третий.
- Заголовок должен кратко и однозначно описывать содержание раздела.
- Для одинаковых типов разделов необходимо использовать одинаковые формулировки заголовков.

### Списки

- Нумерованные списки используются только для последовательности действий, где порядок имеет значение.
- Маркированные списки используются для независимых элементов, характеристик и перечислений.
- Элементы одного списка должны иметь одинаковую грамматическую структуру.
- Не следует смешивать полные предложения и отдельные словосочетания внутри одного списка без необходимости.

### Команды и код

- Команды терминала оформляются отдельными блоками кода с указанием языка bash.
- JSON-фрагменты оформляются блоками с указанием языка json.
- YAML-конфигурации оформляются блоками с указанием языка yaml.
- Python-код оформляется блоками с указанием языка python.
- Короткие имена файлов, каталогов, параметров, команд и переменных внутри текста оформляются как inline code.
- В блоках кода не следует использовать реальные токены, пароли или другие секретные значения.

### Терминология

- Для одного объекта во всей документации используется одно и то же название.
- Полное название «Telegram-бот MenshikovAI» используется при первом упоминании. Далее допускается название «MenshikovAI».
- Названия библиотек, технологий, классов, файлов и параметров пишутся в соответствии с их официальным или фактическим написанием.
- Не допускается произвольное чередование терминов «модель», «классификатор», «ML-модуль» для обозначения одного компонента, если это может создавать неоднозначность.
- Сокращение расшифровывается при первом употреблении, если оно не является очевидным для целевой аудитории.

### Стиль изложения

- Предпочтительно использовать активный залог и явно указывать исполнителя действия.
- Инструкции формулируются через действие: «Установите зависимости», «Запустите модуль», «Добавьте раздел».
- Следует избегать неопределенных выражений: «как обычно», «при необходимости», «если все хорошо», «стандартным способом».
- Если действие зависит от условия, условие указывается перед инструкцией.
- Один абзац должен раскрывать одну основную мысль.
- Текст должен быть технически точным и не содержать рекламных характеристик.

### Ссылки и изображения

- Текст ссылки должен описывать назначение перехода. Не используются формулировки «нажмите сюда» и «по этой ссылке» без пояснения.
- Перед изображением необходимо объяснить, что на нем показано и зачем оно приводится.
- Изображение не должно быть единственным источником обязательной информации.
- Для изображений на сайте MkDocs необходимо добавлять альтернативное текстовое описание.

### Единообразие

- Структура технической документации должна соответствовать структуре стайлгайда.
- Один и тот же раздел во всех документах должен называться одинаково.
- Для раздела «О проекте» используется файл `about-project.md`.
- Для раздела «Установка и запуск» используется файл `installation.md`.
- Для раздела «Конфигурация» используется файл `configuration.md`.
- Для раздела «Архитектура и компоненты» используется файл `architecture.md`.
- Для раздела «Данные» используется файл `data.md`.
- Для раздела «Тестирование» используется файл `testing.md`.
- Изменение имени файла, термина или структуры должно быть отражено во всех связанных разделах документации и в конфигурации `mkdocs.yml`.
